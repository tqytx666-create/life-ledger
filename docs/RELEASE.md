# 上线与回滚

## 当前部署方式（2026-09-10 核查）

GitHub Pages 的发布源是 gh-pages 分支根目录，发布类型为 legacy。仓库未跟踪自定义 Actions 工作流；GitHub 存在平台自动的 pages-build-deployment。普通任务分支推送不改变此发布源。发布设置可能变化，每次上线前重新核查仓库 Settings → Pages / Actions。

现有 deploy.sh 会依次构建、`git add -A`、自动提交、推 main、收集旧静态资源并强推 gh-pages，最后轮询线上资源。它还存在重试耗尽后未可靠中止等行为，不能把最后输出当作完整成功证明。不要用它完成日常提交或协作同步，本次试点不修改、不执行它。

## 用户确认前准备可审阅结果

1. 提供 PR 和待发布的确切提交，说明功能范围、数据/函数/迁移是否改变。
2. 确认无他人未提交改动；检查完整 diff 与暂存内容，完成 npm ci / npm run build 及相关行为验收。普通前端构建不需要执行 migrations 或维护脚本。
3. 记录当前 main、gh-pages 的提交及线上版本作为回滚依据，保留旧 gh-pages 提交在本地备份分支或标签中，避免强推后丢失。
4. 展示验证证据、未通过项、预计影响和回滚方式，等待用户对该次上线的明确确认。

## 获得确认后

由一位发布负责人在干净、专用的发布目录操作。重新确认批准提交和发布源未变；显式提交已审阅文件，核对发布产物不含秘密或数据。不要直接在多人开发目录运行 deploy.sh。若选择沿用该脚本，需先解决其全量暂存、分支假设、失败处理等问题并单独审阅，否则采用经过审核的显式构建/发布步骤。

发布后核对远端 gh-pages、Pages 部署状态、页面加载和关键静态资源，记录实际发布时间及发布提交。数据库、函数部署是独立操作，不能由前端发布授权自动推导。

## 回滚

先明确要恢复的已保存 gh-pages 提交及当前远端提交，经用户确认回滚范围后，由发布负责人将 gh-pages 恢复为保存的版本；如需要重写远端历史，使用精确预期旧值的 force-with-lease，避免覆盖其他发布。随后验证 Pages 部署与线上资源。前端回滚不能撤销数据库迁移、函数或数据变更，这些必须另拟方案。
